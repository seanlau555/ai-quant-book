# 第 19 課：Execution 系統 - 從信號到真實成交

> **如果你將「市場價格」當作「成交價格」，你訓練出來的就不是交易系統，而是一場幻覺。**

---

## 一個常見的致命誤解

許多策略的 backtest 看起來很漂亮，因為它們假設了一個不可能成立的前提：

> 只要 signal 一出現，我就永遠可以按理想價格（例如 K 線 Close）成交。

一旦上線，你立即會遇到三個現實：**slippage、latency，以及 partial／no fill**。這些並非「優化項目」，而是決定策略能否部署的生死線。

本章將助你深入理解甚麼是 **Real Execution Data**，以及它為何是 Execution Agent 的基礎。

---

## 19.1 核心定義

所謂「真實成交數據」，並不是你在 K 線圖上看到的顯示價格，而是：

> **核心邏輯**：如果你當時真的落了盤，最終以甚麼價格成交、成交了多少數量、經歷了多少延遲。

這是理論 backtest 與 live trading 之間最重要的分水嶺。

---

## 19.2 真實 Execution 的四大組成部分

要準確模擬真實交易，必須考慮以下四個關鍵維度：

### 19.2.1 Execution Price

實際成交價通常與 K 線價格（OHLC）有顯著差異。
- **區分**：5 分鐘 K 線的 close price 只是最後一筆成交記錄，並不代表你的大額訂單可以全數按此價成交。
- **拆單**：大額交易中，你的訂單可能被拆成多次成交，價格略有不同，最終呈現為**成交量加權平均價**。

### 19.2.2 Slippage

Slippage 是理論成交價與實際成交價之間的偏差。它是量化交易中主要的隱性成本，主要來自：
- **流動性深度**：買賣盤深度不足以承接訂單量。
- **Market Impact**：你自己的訂單改變了短期供求，令價格朝不利方向移動。
- **價格 Volatility**：在快速市況下，價格瞬間變化。

### 19.2.3 Fill Probability 與 Latency

在真實市場中，落盤不保證成交：
- **Market Order**：追求「即時成交」，代價是往往要承受較大的 slippage。
- **Limit Order**：追求「價格確定性」，但要面對以下風險：
  - **No fill**：價格從未到達你的價位。
  - **Partial fill**：排在你前面的訂單太多，輪到你時流動性已被耗盡。

### 19.2.4 摩擦成本與交易規則

除價格本身外，你還必須支付強制性的「入場費」：
- **顯性成本**：佣金、印花稅、過戶費。
- **規則約束**：最小 tick size、漲跌停限制、特定撮合規則（價格優先、時間優先）。

---

## 19.3 策略視角：為何高頻趨勢策略極度敏感

對於採用 **5 分鐘趨勢 + 高頻交易**邏輯的策略，真實成交數據的重要性會放大數倍。

### 19.3.1 誤差的長期累積

如果你每日交易數十至數百次，即使每筆交易只有 **0.01%** 的成交價偏差，經過複利與高頻累積，也會從根本上扭曲長期 backtest 曲線。

### 19.3.2 「K 線收市價成交」的幻覺

如果在訓練 AI Agent 或 backtest 時，單純把「K 線 Close 價」當作成交價，模型會學到極度危險的邏輯：
- **誤判**：「K 線一完結，我永遠可以即時按收市價成交。」
- **幻覺**：「突破之後，我永遠可以按最佳突破價買入。」

> **現實**：在現實中，於當前 K 線完結時觀察到 signal 後，你最快也只能在**下一根 K 線**開始時落盤。在波動市況下，你幾乎不可能按觀察到的 Close 價成交。

---

## 19.4 典型陷阱：缺乏真實數據導致實盤脫節

當系統性地高估 signal 質素時，策略（尤其是 RL 模型）會產生一系列致命偏差：

### 19.4.1 偏好「無法實現」的入場時機

Agent 會演化出對「剛剛收市突破」signal 的病態偏好。在模擬世界中，突破點就是完美入場價；但在現實中，由於下一根 K 線經常出現裂口或嚴重 slippage，Agent 學到的是**在真實世界永遠買不到的理想時機**。

### 19.4.2 變成「手續費收割機」

在無 slippage 及低摩擦的假設下，AI 認為「多交易一次 = 多賺一次」，瘋狂提高交易頻率。然而在 live trading 中，高頻交易往往是**成本放大器**，最終令實盤表現與模擬結果完全脫鉤。

### 19.4.3 錯誤的因果推斷

最危險的情況是 RL 學到錯誤的因果關係。例如：
- **錯誤推斷**：「指標達到門檻並剛剛收市時，買入必定獲利。」
- **真實因果**：這只是被**理想化 execution 假設**放大的統計假象，並非真正的市場獲利邏輯。

---

## 19.5 兩個數據維度：市場層面環境 vs. 策略 Execution 表現

要獲取真實成交數據，先要弄清楚你需要哪一類數據。我們可以將它分為兩個維度：

- **維度 A：市場真實 Execution 環境數據**（公開環境）：這類數據回答「如果在該市場環境下落盤，**一般**會發生甚麼事？」
- **維度 B：策略的真實市場 Execution 數據**（私有表現）：這類數據回答「當**我的** Agent 在真實市場落盤時，**具體**發生了甚麼事？」

> **核心策略**：如果你想訓練「execution 類」或「online RL Agent」，最終目標必然是取得**維度 B** 的數據。維度 A 只能在早期演算法開發及 cold-start 階段作為近似替代。

---

## 19.6 獲取途徑：如何取得高保真交易數據？

### 19.6.1 第一類：可購買或可經 API 取得的「市場層面數據」

這類數據代表「市場事實」，反映當時整體市場的流動性。

1. **Level-2 / Order Book 數據**（最關鍵）：
   - **內容**：每個買賣檔位的價格與數量、毫秒級 tick／成交記錄。
   - **用途**：估算 market order 平均 slippage、limit order fill probability，以及建立 **Execution Simulator**。
   - **來源**：官方交易所（最權威但昂貴）、專業數據供應商（如 Refinitiv），或部分進階 broker API。

2. **Tick Data**：
   - 看不到 order book 排隊情況，但能看到每一筆實際成交的價格與數量，遠比 K 線準確。

3. **Paper Trading 環境**：
   - **警告**：大部分 paper trading 環境的 slippage 過於理想，亦不考慮你的訂單所造成的 market impact。它只能作為過渡，不要過度依賴。

> **數據來源：學習 vs. Production**
>
> Yahoo Finance 足以應付日線級別的學習練習及 backtest。但它**不適合 production**：數據到達的延遲不穩定、歷史調整可能事後改動、real-time streaming 亦不可靠。對於需要 real-time L1/L2 數據的 production 系統，你需要機構級供應商，例如 **Databento**（標準化的多交易所 tick data）、**Polygon.io**（現已改名為 Massive）（美股），或**交易所直連 feed**（latency 最低、成本最高）。數據質素的躍升伴隨成本的躍升，請把這當作一項真實的預算項目，而非事後才考慮。

### 19.6.2 第二類：必須由「你自己產生」的真實 Execution 數據

這是唯一能真正反映「你的 Agent + 市場」互動的數據，包含完整的訂單生命週期：
- **完整 Log**：落盤時間、訂單類型、預期價格、實際成交價（可能多次成交）、execution 延遲、partial fill／未成交記錄、手續費等。

---

## 19.7 殘酷真相：為何核心數據無法購買

許多開發者問：「我可否直接買這些包含 slippage 的真實數據，而不用實際交易？」

> **核心邏輯**：答案是**不可以**。

原因是：**Slippage 並非純粹的市場屬性，而是「你的行為 + 市場反饋」的共同產物。**

你的落盤方式（market／limit）、訂單規模和落盤時機，都會在 order book 中產生不同的化學反應。世上並不存在「通用的、已經替你執行過」的真實數據集。

---

## 19.8 演進路徑：由 Simulator 到實盤反饋的三個階段

對於追求真實有效性的開發者，建議的工程路徑如下：

1. **階段 1：建立 Execution Simulator**
   - 使用 Level-2／Tick 數據建立一個「保守」的 simulator。
   - 目標：淘汰 80% 在理想假設下賺錢、但在保守假設下蝕錢的策略。

2. **階段 2：小資金實盤（Cold Start）**
   - 以極小倉位進入實盤，目的不是賺錢，而是收集完整 log。
   - 目標：取得真實的 execution 失敗、極端 slippage 與 latency 樣本。

3. **階段 3：數據閉環校準**
   - 利用實盤產生的 B 類數據，反向驗證階段 1 的 simulator，令模擬環境愈來愈貼近你的真實 execution 表現。

## 19.9 Canonical Data Model 與 Symbol Normalization

### 19.9.1 為何需要 Canonical Data Model

不同 broker 與數據供應商使用不同的 symbology：Interactive Brokers 用 `conId`，Bloomberg 用 FIGI，Yahoo Finance 用自己的 ticker 格式，交易所則用原生代碼。如果讓 broker 專屬格式滲入你的核心邏輯，更換交易場所或加入第二個 broker 就會變成重寫。

解決方案是一個**標準化的內部格式**，並為每個交易場所配一個薄薄的 adapter：

```
Internal symbol format: SYMBOL.EXCHANGE
Examples: AAPL.NASDAQ, 0700.HKEX, TSLA.NASDAQ, 9988.HKEX

Normalizer interface (per venue):
  to_internal(broker_symbol) -> canonical_symbol
  to_broker(canonical_symbol) -> broker_symbol
```

這個 canonical model 正是實現多場所交易的關鍵。你的 Signal Agent、Risk Agent 及 portfolio 邏輯全部以標準化 symbol 運作。只有 Execution Agent 的場所 adapter 才會在邊界處轉換為 broker 原生格式。

### 19.9.2 Symbol Resolution 的陷阱

Symbol 對應聽起來簡單，直至邊緣情況摧毀你的 PnL：

| 陷阱 | 會發生甚麼 | 防禦方法 |
|--------|-------------|---------|
| **已除牌的 ticker** | 查詢靜默地返回過時或空白數據 | 每日對照現行有效 symbol 清單驗證 |
| **Corporate action 拆股** | GOOG 變成 GOOGL，ticker 在歷史中途改變 | 追蹤 symbol 變更事件，維護別名表 |
| **多段式 ticker** | `BRK.B` 與 `SYMBOL.EXCHANGE` 格式衝突 | 使用不會衝突的分隔符（例如 `BRK-B.NYSE`） |
| **過時報價** | 數據供應商把昨日收市價當作「現價」返回 | 為每個報價加時間戳；超過門檻即拒絕 |
| **雙重上市證券** | 同一間公司，在不同交易所有不同 symbol | 對應到 canonical entity ID，而不只是 ticker 字串 |

> **經驗法則**：永遠不要相信 ticker 字串是穩定的識別碼。Ticker 會改變、會被重用、在不同場所亦各不相同。請圍繞 canonical ID 建立系統，把 ticker 只當作顯示層的便利。

## 19.10 交易場所選擇：實用的預設選項

對於中小型量化基金，**Interactive Brokers（IB）**是實用的預設交易場所。它以單一 API 涵蓋美股與港股市場，提供原生 algorithmic order type（TWAP、VWAP、Adaptive），並開放真實 execution 數據供 TCA 使用。其佣金結構具競爭力，TWS API 文檔齊備，只是不算優雅。

**Alpaca** 及類似平台適合作為 paper trading 與學習的踏腳石。但它們並非 production 端點：市場覆蓋有限、訂單類型簡化、execution 報告不夠細緻，不足以應付嚴肅的實盤交易。

| 特性 | Interactive Brokers | Alpaca | Paper Trading |
|---------|-------------------|--------|---------------|
| 市場 | 美、港、歐、亞洲 | 僅美國 | 模擬 |
| Algo 訂單 | TWAP, VWAP, Adaptive | 基本 market/limit | 不適用 |
| TCA 數據 | 完整成交報告 | 有限 | 無 |
| 沽空 | 可以（需借貨） | 有限 | 模擬 |
| 用途 | Production | 學習／原型 | 策略驗證 |

## 19.11 實務建議：5 分鐘高頻策略的務實方案

結合 5 分鐘趨勢策略的特點，我最務實的建議是：

- **寧可高估風險**：建立模型時，寧可高估 slippage、低估 fill probability。
- **分開 RL 訓練**：初期先讓 RL Agent 學習「execution 邏輯」（例如落多少單、是否追價、何時放棄），而不是急於學習「方向預測」。
- **盡早上線**：策略在「保守 simulator」中表現穩定後，盡快開始小資金實盤。

---

## 19.12 總結

**顯示價格 + Slippage + 概率性 Latency + 交易摩擦 = 真實成交數據**

只有把所有這些細節都納入考慮，避開「理想化 execution」的陷阱，量化策略（尤其是 AI 驅動的策略）的 backtest 結果才有真正的實際參考價值。由「市場數據」跨越到「成交數據」，是專業量化交易員的必經之路。

---

## 19.13 Multi-Agent 視角

- **Execution Agent**：將「signal」轉化為可執行的訂單（拆單／限價／追價／撤單），並持續量度 execution 質素（slippage、fill rate、latency）。
- **Risk Agent**：將「可以執行」轉化為「值得執行」，對高 slippage／低流動性／異常 latency 的情況觸發減倉或拒絕訂單。
- **Data/Telemetry Agent**：沉澱 execution 數據閉環（訂單 -> 成交 -> 成本 -> PnL），為後續的重播、attribution 與 online learning 提供素材。
